# Phase 4c — Menu CRUD Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a restaurant owner build a whole menu from nothing — create, rename, hide, delete and reorder categories and dishes, and manage variants — so onboarding a client stops requiring hand-written SQL.

**Architecture:** New write methods land in the tenant-bound `core/menu/repository.ts`, which never accepts a `tenantId` from a caller and filters on it in every statement anyway. Server Actions in `src/app/admin/[tenantId]/actions.ts` are the only route to them, each re-checking membership itself. The admin menu page becomes a builder made of small client components, with a quick-add row per category so 90 dishes can be typed in one sitting.

**Tech Stack:** Next.js 16.2.12, React 19, TypeScript strict, Drizzle + PostgreSQL 17, Zod v4, Tailwind v4, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-08-08-menu-crud-design.md`

## Global Constraints

- **No migration.** `sortOrder` already exists on `categories` and `items`; this is application work only.
- **`src/core/` must not import `next/*`, `react`, or `react-dom`.** ESLint-enforced, CI-blocking.
- **`core/` never reads `process.env`.** Factories receive config; wiring lives in `src/server/`.
- **Repositories never accept `tenantId` from a caller.** It comes from the `TenantSession`, and every statement filters on it even though RLS also enforces it.
- **Never `Promise.all` queries sharing a transaction.** Sequential awaits inside `withTenant` — a transaction is pinned to one connection and PostgreSQL cannot serve concurrent queries on it.
- **Every admin Server Action calls `requireMembership` itself.** A layout guard does not run when an action is invoked directly, and `tenantId` arrives from the client.
- **Never `redirect()` from an admin Server Action.** Return a target; the client calls `window.location.assign()`.
- **`revalidatePath(\`/${membership.tenantId}\`)` after every mutation**, matching the existing actions in that file.
- **Money is integer minor units.** Convert with `toMinorUnits(major, currency)` / `toMajorUnits(minor, currency)` — never hardcode the exponent.
- **Localization is paired columns.** `nameAr` is optional and stored as `null` when blank, never `""`.
- **Ids arriving from the client are parsed as UUIDs at the action boundary.** A non-UUID string reaching a `WHERE id = $1` raises a cast error rather than matching nothing, so this validation is load-bearing.
- **Every client mutation control calls `router.refresh()` after a successful action.** One uniform rule, so nothing depends on guessing whether a given action shape triggers a re-render.
- **E2E isolation is by DATA, never by ordering.** Any spec that writes takes a sandbox fixture.
- **`npm run verify` must pass before any task is considered done.**
- **PATH first, every fresh shell:** `$env:Path = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + [Environment]::GetEnvironmentVariable('Path','User')`
- **Browser suite runs as `E2E_PORT=3100 npm run test:e2e`.** On 3000 it silently reuses whatever `npm run dev` is serving and reports it as a pass.

```ts
    async findCategory(categoryId: string): Promise<Category | null> {
      const rows = await tx
        .select()
        .from(categories)
        .where(
          and(eq(categories.tenantId, tenantId), eq(categories.id, categoryId)),
        )
        .limit(1);
      return rows[0] ?? null;
    },

    async updateCategory(
      categoryId: string,
      changes: Partial<
        Pick<NewCategory, "nameEn" | "nameAr" | "isVisible" | "sortOrder">
      >,
    ): Promise<Category | null> {
      const [row] = await tx
        .update(categories)
        .set({ ...changes, updatedAt: new Date() })
        .where(
          and(eq(categories.tenantId, tenantId), eq(categories.id, categoryId)),
        )
        .returning();
      return row ?? null;
    },

    /**
     * Deletes a category AND, through `items.category_id ON DELETE CASCADE`,
     * every dish under it.
     *
     * Returns the deleted row so the caller can name what went; null means the
     * id belonged to another restaurant, or to nothing.
     */
    async deleteCategory(categoryId: string): Promise<Category | null> {
      const [row] = await tx
        .delete(categories)
        .where(
          and(eq(categories.tenantId, tenantId), eq(categories.id, categoryId)),
        )
        .returning();
      return row ?? null;
    },

    /**
     * The blast radius of deleting a category, for the confirmation to name.
     * Counted from the database rather than from whatever the page rendered
     * some minutes ago -- a stale count turns "and its 14 dishes" into a lie.
     */
    async countItemsInCategory(categoryId: string): Promise<number> {
      const [row] = await tx
        .select({ value: count() })
        .from(items)
        .where(
          and(eq(items.tenantId, tenantId), eq(items.categoryId, categoryId)),
        );
      return row?.value ?? 0;
    },

    /**
     * Appends rather than prepends: a new category belongs at the end of the
     * menu until the owner moves it. max + 1, never count, so deleting a row in
     * the middle cannot hand out a sort order that is already taken.
     */
    async nextCategorySortOrder(): Promise<number> {
      const [row] = await tx
        .select({ value: max(categories.sortOrder) })
        .from(categories)
        .where(eq(categories.tenantId, tenantId));
      return (row?.value ?? -1) + 1;
    },
```

    /**
     * Rewrites every category's sort order from its position in `orderedIds`.
     *
     * The full ordered list rather than a "move up" delta: two open tabs each
     * sending a swap can interleave into an order neither owner asked for,
     * whereas the last full list to land is at least coherent.
     *
     * An id belonging to another restaurant simply matches no row -- the
     * tenantId filter sees to that -- so a stale or hostile list degrades to
     * reordering the rows it legitimately names, rather than failing entirely.
     *
     * Sequential, never Promise.all: these share one transaction, and therefore
     * one connection.
     */
    async reorderCategories(orderedIds: readonly string[]): Promise<void> {
      for (const [index, id] of orderedIds.entries()) {
        await tx
          .update(categories)
          .set({ sortOrder: index, updatedAt: new Date() })
          .where(
            and(eq(categories.tenantId, tenantId), eq(categories.id, id)),
          );
      }
    },

    /** Same contract as reorderCategories, scoped to one category's dishes. */
    async reorderItems(
      categoryId: string,

export async function updateCategory(
  tenantId: string,
  categoryId: string,
  changes: { nameEn?: string; nameAr?: string; isVisible?: boolean },
): Promise<MenuActionState> {
  const { membership } = await requireMembership(uuid.parse(tenantId));
  const id = uuid.parse(categoryId);

  const patch: {
    nameEn?: string;
    nameAr?: string | null;
    isVisible?: boolean;
  } = {};

  if (changes.nameEn !== undefined) {
    const parsed = categoryInput
      .pick({ nameEn: true })
      .safeParse({ nameEn: changes.nameEn });
    if (!parsed.success) {
      return { error: parsed.error.issues[0]?.message ?? "Check the form." };
    }
    patch.nameEn = parsed.data.nameEn;
  }
  if (changes.nameAr !== undefined) {
    patch.nameAr = changes.nameAr.trim() || null;
  }
  if (changes.isVisible !== undefined) {
    patch.isVisible = changes.isVisible;
  }

  const row = await withTenant(db, membership.tenantId, (session) =>
    createMenuRepository(session).updateCategory(id, patch),
  );
  if (!row) return { error: "That section no longer exists." };

  revalidatePath(`/${membership.tenantId}`);
  return { error: null, saved: true };

export async function deleteCategory(
  tenantId: string,
  categoryId: string,

  const id = uuid.parse(categoryId);

    // Counted BEFORE the delete: afterwards the rows are gone and any number
    // reported to the owner would be a guess. Sequential -- one transaction,

    createMenuRepository(session).reorderCategories(parsed.data),
  );

  revalidatePath(`/${membership.tenantId}`);
  return { error: null, saved: true };
}

      </span>

        disabled={pending}

              setAsking(false);

      </button>

"use client";

import { useRouter } from "next/navigation";
import { useState, useTransition } from "react";
import { ConfirmDelete } from "./confirm-delete";
import {
  deleteCategory,
  reorderCategories,
  updateCategory,
  type MenuActionState,
} from "./actions";

const ghost =
  "rounded-md border border-[var(--color-rule)] px-2 py-1 text-[0.75rem] text-[var(--color-muted)] hover:text-[var(--color-ink)] disabled:opacity-40";

const field =
  "rounded-md border border-[var(--color-rule)] bg-transparent px-2 py-1 text-[0.9rem]";

/**
 * Reorder by buttons, not by drag.
 *
 * The roadmap asked for drag. Drag is fine on a laptop and genuinely bad on a
 * phone: a long list, one thumb, and a scroll gesture competing with the drag.
 * This admin is used standing in a kitchen, so the mobile experience wins.
 * Buttons also work from a keyboard and are announced by screen readers.
 *
 * The FULL ordered list goes to the server, never a "move up" delta: two open
 * tabs each sending a swap can interleave into an order neither owner asked
 * for, whereas the last full list to land is at least coherent.
 */
export function MoveControls({
  label,
  orderedIds,
  id,
  onMove,
}: {
  /** Names the thing being moved, e.g. "Grills". */
  label: string;
  orderedIds: readonly string[];
  id: string;
  onMove: (ordered: string[]) => Promise<MenuActionState>;
}) {
  const [pending, startTransition] = useTransition();
  const router = useRouter();

  const index = orderedIds.indexOf(id);
  const first = index <= 0;
  const last = index === orderedIds.length - 1;

  function move(delta: -1 | 1) {
    const next = [...orderedIds];
    const target = index + delta;
    const moved = next[index];
    const displaced = next[target];
    if (moved === undefined || displaced === undefined) return;
    next[index] = displaced;
    next[target] = moved;

    startTransition(async () => {
      await onMove(next);
      router.refresh();
    });
  }

  return (
    <>
      <button
        type="button"
        aria-label={`Move ${label} up`}
        disabled={pending || first}
        onClick={() => move(-1)}
        className={ghost}
      >
        ↑
      </button>
      <button
        type="button"
        aria-label={`Move ${label} down`}
        disabled={pending || last}
        onClick={() => move(1)}
        className={ghost}
      >
        ↓
      </button>
    </>
  );
}

  categoryId,

  nameAr,

  itemCount,

  const [error, setError] = useState<string | null>(null);

  const router = useRouter();

      const result = await updateCategory(tenantId, categoryId, {
        nameEn: draftEn,
        nameAr: draftAr,
      });
      if (result.error) {
        setError(result.error);
        return;
      }

      setRenaming(false);
      router.refresh();
    });

            setRenaming(false);

          className={ghost}
        >
          Cancel

        {error ? (

            {error}
          </p>
        ) : null}
      </form>
    );
  }

  return (

```ts
async function provisionEmpty(
  projectName: string,
  parallelIndex: number,
): Promise<EmptySandbox> {
  const connectionString = process.env.MIGRATION_DATABASE_URL;
  if (!connectionString) {
    throw new Error(
      "MIGRATION_DATABASE_URL must be set: the browser suite provisions a " +
        "tenant per project, which is an operator-role action. Copy " +
        ".env.example to .env.local and fill it in.",
    );
  }

  const slug = `${slugFor(projectName, parallelIndex)}-empty`;
  const name = `E2E ${projectName} ${parallelIndex} empty`;
  const owner = `owner@${slug}.test`;
  const pool = new Pool({ connectionString, max: 1 });
  const client = await pool.connect();

  try {
    // Sequential awaits throughout: a transaction is pinned to one connection.
    await client.query("BEGIN");

    const tenantId = await upsertTenant(client, slug, name);

    await client.query(
      `INSERT INTO domains (tenant_id, hostname, is_primary, verified_at)
       VALUES ($1, $2, true, now())
       ON CONFLICT (hostname) DO UPDATE
         SET tenant_id = EXCLUDED.tenant_id, verified_at = now()`,
      [tenantId, `${slug}.localhost`],
    );

    // Genuinely empty, every run. The test's whole claim is that an owner can
    // start from nothing, so starting from the previous run's leftovers would
    // quietly stop testing that.
    await client.query("DELETE FROM categories WHERE tenant_id = $1", [
      tenantId,
    ]);
    await client.query("DELETE FROM media WHERE tenant_id = $1", [tenantId]);

    // A known theme, so the public assertions do not depend on whatever a
    // previous run left behind.
    await client.query(
      `INSERT INTO theme_settings (tenant_id, palette_id, font_pair, preset, palette, logo_id)
       VALUES ($1, 'paper', 'classic', 'list', '{}'::jsonb, NULL)
       ON CONFLICT (tenant_id) DO UPDATE
         SET palette_id = EXCLUDED.palette_id,
             font_pair  = EXCLUDED.font_pair,
             preset     = EXCLUDED.preset,
             palette    = EXCLUDED.palette,
             logo_id    = EXCLUDED.logo_id`,
      [tenantId],
    );

    const passwordHash = await hashPassword(SANDBOX_PASSWORD);
    const user = await client.query<{ id: string }>(
      `INSERT INTO users (email, name, password_hash)
       VALUES ($1, $2, $3)
       ON CONFLICT (email) DO UPDATE SET password_hash = EXCLUDED.password_hash
       RETURNING id`,
      [owner, slug, passwordHash],
    );
    const userId = user.rows[0]?.id;
    if (!userId) throw new Error(`Upsert returned no user row for ${owner}`);

    await client.query(
      `INSERT INTO memberships (tenant_id, user_id, role)
       VALUES ($1, $2, 'owner')
       ON CONFLICT (tenant_id, user_id) DO UPDATE SET role = 'owner'`,
      [tenantId, userId],
    );
    // Exactly one membership, so signing in redirects straight to the tenant.
    await client.query(
      "DELETE FROM memberships WHERE user_id = $1 AND tenant_id <> $2",
      [userId, tenantId],
    );

    // Failures from earlier runs are still inside the limiter's 15-minute
    // window and would answer "too many attempts" to a test asserting on
    // something else entirely.
    await client.query("DELETE FROM login_attempts WHERE identifier = $1", [
      owner,
    ]);

    await client.query("COMMIT");

    return {
      id: tenantId,
      slug,
      name,
      site: site(`${slug}.localhost`),
      owner,
      password: SANDBOX_PASSWORD,
    };
  } catch (error) {
    await client.query("ROLLBACK");
    throw error;
  } finally {
    client.release();
    await pool.end();
  }
}
```

import { type Page } from "@playwright/test";

/**
 * Onboarding, as a test rather than as a hope.
 *
 * The product's central claim is that a restaurant goes live the same day, with
 * its menu typed in during the sale. That claim is only true if an owner can
 * start from a tenant with nothing in it and end with a menu on their site --
 * so this walks exactly that path, on a tenant that is genuinely empty.
 *
 * Its tenant is provisioned per Playwright project and per parallel slot by the
 * `emptySandbox` fixture, and wiped clean each run. Isolation is by data, never
 * by ordering.
 */
test.describe.configure({ mode: "serial" });

async function signIn(page: Page, sandbox: EmptySandbox) {
  await page.context().clearCookies();
  await page.goto(`${ADMIN}/login`);
  await page.getByLabel("Email").fill(sandbox.owner);
  await page.getByLabel("Password").fill(sandbox.password);
  await page.getByRole("button", { name: "Sign in" }).click();
  // Wait for login to actually leave /login before navigating on: the redirect
  // is a real request, and racing it lands on a page that is about to be
  // replaced.
  await page.waitForURL(new RegExp(`/${sandbox.id}$`), { timeout: 15_000 });
  // A click before React hydrates hits a button with no handler and does
  // nothing at all -- which is what a real owner gets tapping too early.
  await page.waitForLoadState("networkidle");
}

/** Adds one dish through the quick-add row and waits for the server. */
async function quickAdd(
  page: Page,
  section: string,
  name: string,
  price: string,
) {
  await page.getByLabel(`New dish in ${section}`).fill(name);
  await page.getByLabel(new RegExp(`^Price for new dish in ${section}`)).fill(price);
  await page.getByLabel(`New dish in ${section}`).press("Enter");

  // Wait for the dish to appear in the list, not for the input to clear.
  // Clearing happens the moment the action returns; the row only renders once
  // the server has the dish. Waiting on the weaker signal races the next step.
  await expect(
    page.getByRole("link", { name: new RegExp(name) }),
  ).toBeVisible();
}

test("builds a menu from nothing and puts it on the site", async ({
  page,
  emptySandbox,
}) => {
  await signIn(page, emptySandbox);

  // Nothing yet -- and the page says what to do rather than rendering an empty
  // shell.
  await expect(
    page.getByRole("heading", { name: /build your menu/i }),
  ).toBeVisible();

  // 1. A section.
  await page.getByLabel("New section").fill("Mezze");
  await page.getByLabel("Arabic name (optional)").fill("مقبلات");
  await page.getByRole("button", { name: "Add section" }).click();
  await expect(page.getByRole("heading", { name: /Mezze/ })).toBeVisible();

  // 2. Three dishes, without leaving the page once.
  await quickAdd(page, "Mezze", "Hummus", "6.50");
  await quickAdd(page, "Mezze", "Fattoush", "8");
  await quickAdd(page, "Mezze", "Tabbouleh", "7.25");

  // Focus stays where the next dish gets typed -- the whole reason quick-add
  // exists.
  await expect(page.getByLabel("New dish in Mezze")).toBeFocused();

  // 3. Reorder: Tabbouleh above Fattoush.
  await page.getByRole("button", { name: "Move Tabbouleh up" }).click();
  await expect(
    page.getByRole("link", { name: /Tabbouleh/ }),
  ).toBeVisible();

  // 4. Delete one, with a confirmation that names it.
  await page.getByRole("button", { name: "Delete Fattoush" }).click();
  await expect(page.getByText("Delete Fattoush?")).toBeVisible();
  await page.getByRole("button", { name: "Yes, delete" }).click();
  await expect(page.getByRole("link", { name: /Fattoush/ })).toHaveCount(0);

  // Reload before asserting the order: everything above proves what the browser
  // drew, and a fresh render is what proves it reached the database.
  await page.goto(`${ADMIN}/${emptySandbox.id}`);
  const adminNames = page.locator("main ul li a span:first-child");
  await expect(adminNames).toHaveText(["Hummus", "Tabbouleh"]);

  // 5. The customer's view. This is the claim: typed during the sale, live the
  // same day.
  await page.goto(emptySandbox.site);
  await expect(page.getByRole("heading", { name: "Mezze" })).toBeVisible();
  await expect(page.getByRole("heading", { name: "Hummus" })).toBeVisible();
  await expect(page.getByRole("heading", { name: "Tabbouleh" })).toBeVisible();
  await expect(page.getByRole("heading", { name: "Fattoush" })).toHaveCount(0);
  await expect(page.getByText("$6.50")).toBeVisible();
});

**Deviations from the spec, stated:**

1. **`updateCategory` is one action taking a `changes` object**, not a FormData action. It serves both rename and hide/show, which are two different controls with the same write; splitting it would have duplicated the membership check and the revalidate for no gain. The repository method keeps the name the spec gives it.
2. **`AddCategory` takes an Arabic name too.** The spec says "a single input". There is no category edit page to add Arabic on later, and a restaurant with an Arabic-default site needs its section headings in Arabic — one extra optional field is cheaper than a screen that does not exist. Rename offers both as well.
3. **Three repository methods the spec does not list** — `findCategory`, `nextCategorySortOrder`, `nextItemSortOrder` (plus `nextVariantSortOrder`). The `next*` ones make a new row land at the end of its list rather than at position 0. `findCategory` closes a real hole: `items.category_id` is a foreign key, PostgreSQL checks foreign keys as the table owner, and that bypasses RLS — so a client-supplied `categoryId` has to be looked up in tenant scope before it is trusted.
4. **Task 4 stops `tenant-isolation.test.ts` truncating.** Not in the spec, but Task 1 adds a second database-backed test file and Vitest runs files concurrently; leaving the truncate would make the two files delete each other's fixtures at random.
